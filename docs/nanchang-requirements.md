# 南昌版智能旅行助手 — 需求文档

> 状态:需求确认中(2025 拍板,待实施)
> 技术栈:前端 Vue3 + TypeScript + Ant Design Vue;后端 Python + FastAPI + LangChain/LangGraph + 高德 MCP + 千问 Embedding + ChromaDB + 混合检索 + 规划后处理

---

## 一、项目定位

在现有「智能旅行助手」基础上改造为**专门面向南昌**的旅行规划产品:
- 真实用户账号体系(登录区分、个性化记忆);
- **RAG 知识增强**:清洗切片南昌本地知识(攻略/景点/美食/拍照点/交通枢纽/营业时间)并向量化,
  以**关键词 + 向量混合检索**为模型补充本地知识,**来源约束 + 结构化输出 + 规划后处理**
  降低路线冲突与内容幻觉。

## 二、已确认的核心决策

| 决策项 | 结论 |
|---|---|
| 目标城市 | **南昌**(固定,去掉城市选择) |
| 登录方式 | 用户名 + 密码(bcrypt 加密,JWT 认证) |
| 游客模式 | 游客可用核心功能;登录后记忆/历史行程才持久生效 |
| 数据库 | SQLite(用户/行程/知识关键词索引) |
| 历史行程 | 保存并可回看(列表 / 重新打开 / 删除) |
| RAG 知识增强 | **开启**:精选南昌本地知识 → 清洗切片向量化 → 混合检索 → 来源约束 + 结构化输出 + 规划后处理 |
| 知识数据来源 | **我(助手)基于公开资料代整理初版**(官网/百科/攻略站,标注来源,内容需用户确认) |
| 关键词检索实现 | **rank_bm25 内存索引**(纯 Python、零依赖,南昌知识量级完全够用) |
| 知识摄取方式 | **离线脚本为主 + 在线调试接口**(批量重建一条命令;接口便于联调) |

## 三、功能需求

### 3.1 用户账号体系(新增)

- 注册(用户名唯一、密码 ≥6 位)、登录/登出、JWT 认证、密码 bcrypt 哈希
- 用户资料:昵称(默认=用户名)、注册时间;头像本期可省略
- 前端:登录页、注册页、顶栏登录态、路由守卫;token 存 localStorage,axios 自动附带 Bearer token
- 认证接口:`POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`

### 3.2 南昌聚焦(改造现有)

- `TripRequest.city` 固定"南昌";POI 搜索/天气/路线自动 citylimit 南昌
- 规划 prompt 强化南昌特色:滕王阁、八一起义纪念馆、万寿宫、南昌之星、绳金塔、秋水广场、赣江两岸灯光秀、拌粉瓦罐汤等
- 首页表单删除城市输入,固定展示"目的地:南昌";品牌文案南昌化
- 结果页地图中心、搜索范围自动南昌

### 3.3 AI 行程规划引擎(对话式增量规划)

> 核心升级:把"一次请求 → 生成完整计划"升级为**状态化、对话式、可增量调整**的规划引擎,
> 用户信息不全可逐步补全,修改只重规划受影响局部,避免每次对话全景重新生成。

#### 3.3.1 规划状态(PlannerState)

基于用户输入构建的结构化状态,贯穿整个规划会话:

| 字段 | 说明 |
|---|---|
| departure_city | 出发地(如"北京") |
| destination | 目的地,**固定南昌** |
| start_date / end_date / travel_days | 出行日期与天数 |
| party | 同行人数(成人/儿童,如 2 大 1 小) |
| budget | 预算(总额,或"人均/天"区间) |
| transportation | 交通方式偏好(高铁/飞机/自驾/市内公共交通) |
| interests | 兴趣标签(历史文化/自然风光/美食/拍照/亲子…) |
| accommodation | 住宿偏好(经济/舒适/豪华/民宿) |
| 派生字段 | missing_fields(缺失参数列表)、current_plan(当前计划)、status(draft/planned/has_conflict) |

#### 3.3.2 参数补全

- 状态不完整时,系统**识别所有缺失字段,一次性列出**让用户批量填写(表单形式,而非逐项追问);
- 支持宽松默认值(留空或选"随便"则用推荐默认),避免卡住;
- 提交后状态更新,再次检查,直到满足生成条件或用户明确要求"先生成一版"。

#### 3.3.3 LangGraph 编排

在现有 StateGraph 基础上扩展为支持对话式增量的编排:

```
用户输入(聊天)
  → [意图识别] 问答 / 行程生成 / 修改指令 / 补全回答
       │
       ├─ 问答 → 走"旅行对话助手"(3.7)
       ├─ 补全回答 → [更新状态] → [参数补全] 继续追问
       ├─ 行程生成 → [冲突检查] → 输出计划(状态齐全时)
       └─ 修改指令 → [局部重规划] → [冲突检查] → 更新 current_plan
```

- 复用现有 `StateGraph` + 多智能体(景点/天气/酒店/规划专家),新增
  `intent` / `fill_params` / `check_conflicts` / `local_replan` 等节点;
- 状态与 `current_plan` 持久化(见 3.3.5 / 数据设计),支持跨轮次增量修改。

#### 3.3.4 局部重规划(避免全景重新生成)

- 用户修改指令 → 解析操作意图与**影响范围**(某天 / 某类 / 某字段);
- 只把受影响局部 + 必要上下文交给 LLM 重新生成,其余部分保持不变;
- 典型指令:
  - "第二天酒店换成经济型" → 只重排第二天的住宿
  - "第三天不去梅岭,改去海昏侯" → 只替换第三天的景点并检查路线
  - "预算降到 2000" → 重算预算/替换高价项,不动整体结构
  - "加一天,变成 4 天" → 在结构上扩展一天并重排相邻天

#### 3.3.5 冲突检查

规划生成/修改后执行(确定性规则 + 知识库 + 高德数据):

| 冲突类型 | 检查方式 |
|---|---|
| 营业时间冲突 | 安排时段 vs 知识库营业时间(周一闭馆、闭园时间) |
| 距离/交通冲突 | 同天景点间距离或预估交通时间超阈值(高德路线) |
| 预算超支 | 各项费用汇总 vs 用户预算 |
| 同行人数匹配 | 亲子/老人场景是否安排合适(步行强度、设施) |
| 重复景点/餐食 | 同天或全程去重 |

冲突结果以 `conflicts[]` 返回(含类型、位置、建议),驱动用户下一步决策或自动修复。


### 3.4 RAG 知识增强(本期核心新增)

#### 3.4.1 知识分类与元数据

| category | 内容示例(南昌) | 关键元数据 |
|---|---|---|
| 攻略 | 精选 1/2/3 日游路线、游玩攻略 | city/category/source/title |
| 景点 | 滕王阁、八一馆、万寿宫、绳金塔、南昌之星、梅岭、海昏侯国遗址等 | + poi_name、坐标、门票 |
| 美食 | 拌粉、瓦罐汤、藜蒿炒腊肉、白糖糕、南昌炒粉、水煮、油炸 | + 代表店铺/街区 |
| 拍照点 | 滕王阁夜景、秋水广场喷泉、南昌之星摩天轮、赣江灯光秀 | + 最佳时段 |
| 交通枢纽 | 昌北机场、南昌站/西站/东站、地铁 1-4 号线 | + 换乘/接驳信息 |
| 营业时间 | 各景点/博物馆开闭园时间、周一闭馆、预约规则 | **结构化字段:poi_name / open_time / close_time / 开放日 / 预约规则** |

每条知识带 `source`(来源:官方页/自编手册/精选攻略),用于**来源约束**与引用展示。

#### 3.4.2 知识处理管道(离线,可脚本化)

```
原始资料(人工整理 + 公开资料,我代整理初版并标注来源)
  → 清洗(去广告噪声、统一格式、纠错)
  → 结构化切片(按标题/小节;chunk 300~500 字、重叠 50~100;营业时间单独结构化)
  → 千问 text-embedding-v3 向量化
  → 双索引入库:
      ├─ 向量索引   ChromaDB(metadata: city/category/source/title/poi_name)
      └─ 关键词索引  rank_bm25 内存索引(存同一切片文本,摄取时构建/重建)
```

**摄取方式**:离线脚本 `python scripts/kb_ingest.py`(清洗→切片→向量化→双索引,支持 `--recreate`);
另提供调试接口 `GET /api/kb/search`、`POST /api/kb/ingest` 便于联调与增量摄取。

#### 3.4.3 混合检索(在线)

- **向量检索**:查询经千问向量化 → ChromaDB 相似度 Top-N
- **关键词检索**:rank_bm25 关键词匹配 Top-N(南昌专有名词如"拌粉""滕王阁"靠关键词召回更稳)
- **融合**:Reciprocal Rank Fusion(RRF)合并两路结果 → Top-K(默认 5)
- **场景过滤**:行程规划时按 category 过滤(景点/营业时间/美食/交通);问答时全类别
- **无结果降级**:检索不到时不阻塞主流程,回退原有生成逻辑

#### 3.4.4 来源约束(Grounding)

- 生成 prompt 明确:**只能使用检索提供的知识,禁止编造;知识不足时明确说明**;
- 每条检索片段携带来源,LLM 输出可引用(`[来源:xxx]`);
- 规划结果中的景点/美食必须能追溯到知识库或高德实时检索结果。

#### 3.4.5 结构化输出

- 规划输出维持 `TripPlan` JSON schema(现有),在 prompt 中注入检索到的知识;
- 问答输出携带 `related_memories` / `sources` 引用字段(现有 ChatResponse 扩展)。

#### 3.4.6 规划后处理(确定性规则,不依赖 LLM)

| 规则 | 说明 | 目标 |
|---|---|---|
| 营业时间校验 | 用"营业时间"知识校验每日景点安排是否在开放时段内;冲突则调序/替换 | 降低路线冲突 |
| 距离/时间校验 | 同一天相邻景点间距离或预估交通时间超阈值 → 提示/调序(结合高德路线) | 降低路线冲突 |
| 去重 | 同一天/全程不重复安排同一景点、同一餐食 | 提升质量 |
| 存在性校验 | 计划中景点名称/坐标与知识库或高德 POI 交叉验证,未命中则标记/替换 | 降低幻觉 |
| 结构校验 | JSON schema 校验、经纬度范围校验(南昌区域)、必填字段补全 | 降低幻觉 |

> 后处理结果建议在响应中附带 `processing_warnings` 列表(如"XX 景点周一闭馆,已调整到次日"),前端可展示。

### 3.5 记忆与个性化(对接现有记忆系统)

- 记忆系统 `user_id` 改为数据库用户 ID;登录用户记忆/偏好画像跨设备持久;游客逻辑保留
- `/api/chat` 个性化问答保留;问答时同样可混合检索南昌知识

### 3.6 历史行程(新增)

- `trips` 表保存 TripPlan JSON;生成成功后自动保存(登录用户)
- 接口:`GET /api/trips`(列表)、`GET /api/trips/{id}`、`DELETE /api/trips/{id}`
- 前端"我的行程"页(卡片列表 → 打开详情复用 Result 页)

### 3.7 旅行对话助手(新增正式功能)

**定位**:用户在旅行途中(或行前)随时提问的"随身助手",聊天式交互,移动端优先。

#### 能力矩阵

| 问题类型 | 示例 | 数据来源 |
|---|---|---|
| 景点/营业时间 | 滕王阁门票多少?现在开门吗? | RAG 知识库(景点/营业时间) |
| 交通导航 | 从八一广场到滕王阁怎么走? | 高德路线 API(实时) |
| 实时天气 | 明天南昌天气如何? | 高德天气 API(实时) |
| 附近美食/POI | 万寿宫附近有什么好吃的? | RAG 美食 + 高德 POI 搜索 |
| 拍照打卡 | 南昌夜景去哪里拍最好? | RAG 拍照点 |
| 行程建议 | 我只有一天时间怎么逛? | RAG 攻略 + 偏好画像 |

#### 技术设计

- **多轮对话**:请求携带最近 N 轮 `chat_history`(前端维护),支持上下文追问("那怎么过去?");
  登录用户会话可持久化回看,游客仅内存会话
- **双路增强**:
  - 南昌知识:混合检索(向量 + rank_bm25 → RRF)注入,回答附 `[来源:xxx]`;
  - 实时工具:意图识别后调用高德(天气/路线/POI 搜索),复用现有 `amap_service`;
- **个性化**:注入用户偏好画像与相关历史记忆(现有记忆系统),如"用户不吃辣"则美食推荐避辣;
- **降级策略**:知识检索无结果、工具调用失败时,基于通用能力回答并明示不确定性;
- **回复附注**:前端展示"来源卡片"与"相关记忆",提升可信度(降低幻觉)。

- 登录用户可查看历史会话(续聊),游客可即时使用但不保存。

## 四、非功能需求

1. 安全:密码 bcrypt;JWT 密钥走环境变量;`.env` 不进 Git
2. 数据隔离:用户数据(记忆/行程/画像)按登录用户 ID 隔离;知识库为公共数据(无用户维度)
3. 兼容:游客体验不回归;现有接口向后兼容
4. 性能:南昌知识库规模(预计几百~两千条切片)下,混合检索应在百毫秒级;BM25 索引随摄取脚本离线构建
5. 可维护:沿用现有分层;新增 planning(规划引擎)/ knowledge(知识)/ retrieval(检索)/ postprocess(后处理)模块

## 五、数据设计草案

```text
users 表(SQLite)
  id / username UNIQUE / password_hash / nickname / role('user'|'admin') / created_at

trips 表(SQLite)
  id / user_id / city='南昌' / plan_json / created_at

planning_sessions 表(SQLite,规划状态持久化,支撑参数补全/局部重规划)
  id / user_id / state_json(PlannerState:出发地/日期/人数/预算/交通/兴趣等)
       / plan_json(current_plan) / status(draft|planned|has_conflict) / updated_at

chat_sessions 表(SQLite,登录用户会话持久化,可选)
  id / user_id / title / created_at / updated_at

知识库(ChromaDB + rank_bm25 关键词索引,公共数据)
  切片文本 + metadata{city:'nanchang', category, source, title, poi_name, ...}
  营业时间条目:结构化字段 open_time/close_time/open_days/booking_rule
```
